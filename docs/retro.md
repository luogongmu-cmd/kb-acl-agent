# 复盘：给 RAG 加权限边界，哪些地方会变

> 对应 8 周路线图第 3–4 周。数据来自 `eval/runs/before.json`：12 条评测，权限内 1.00 / 越权拒答 1.00 / 公共 1.00 / 违规 0。

## 1. 权限放在哪一层，是第一个要定的事

两种做法：

| 做法 | 问题 |
| --- | --- |
| prompt 里写「不要回答无权内容」 | 靠模型自觉，越权问题只要措辞绕一点就可能漏 |
| **检索层按角色过滤**（本项目） | 越权文档根本不进上下文，模型没有机会编 |

选了第二种：ingest 时给每个 chunk 写 `acl_<dept>=1`，查询时 `where={"$or": [{"acl_public": 1}, {"acl_hr": 1}]}`。这是硬边界，不依赖模型。

## 2. 踩过的坑：public 字段写错了

第一版给 HR 文档同时写了 `acl_public=1` 和 `acl_hr=1`，本意是「HR 也能看公共文档」，结果反了——guest 查询 `acl_public=1` 时把 HR 文档也捞了出来。实测时发现 guest 问公司成立时间，sources 里出现了 `hr/考勤制度.md`。

修正：**文档只写自己部门的 ACL 字段**，查询时用 `public OR 本部门` 组合。这个 bug 只有跑起来看 sources 才会发现，光看代码很容易漏。

## 3. 成本控制的三件小事

1. **缓存**：`(role, question)` 为 key，60 秒 TTL。实测第二次相同问题 `cached: true`，省一次检索 + 生成。
2. **限流**：每个角色每分钟 20 次，内存 deque 实现；超限返回 429，而不是让请求排队打满 API。
3. **上下文预算**：最多 5 段 × 400 字，避免一次问答把 token 拉爆。

## 4. 失败降级

检索或生成抛异常时，`/chat` 返回 503 + `检索或生成暂时不可用：<异常类型>`，不把 traceback 甩给用户。这和第一个项目里工具调用的 `TOOL_ERROR` 回灌是同一套思路：**把可行动的原因给到调用方**。

## 5. 与第一个项目的关系

第一个项目证明「检索能跑通、能评测」；这个项目证明「同样的检索，加上权限边界后哪些地方要改」：ingest 多写 ACL 字段、query 多一个 where、API 多一个 role 参数、评测多一类越权样本。面试时两个项目可以连着讲，比讲两个不相干的 Demo 更有说服力。
